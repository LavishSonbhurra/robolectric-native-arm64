# Licensing audit

This is an engineering audit, not legal advice. Nothing here has been cleared by a lawyer.

Scope: what we redistribute when we publish `libandroid_runtime.so` (and a jar that bundles it)
for Linux arm64, SDK 36, built from AOSP `android-16.0.0_r1`. The build scripts, the loader plugin and
the test rig are our own work and are covered in the last sections.

## 1. Summary

We found no blocker for publishing. Everything statically linked into the library is under a
permissive license, the same set of components Google already redistributes in the official
`libandroid_runtime.so` that ships inside Robolectric's `android-all` jar. Robolectric's own POM for the
Android native runtime says the same thing about the model: building from the Apache-2.0 AOSP sources and
distributing the result is allowed (the comment in `nativeruntime/build.gradle.kts` of Robolectric 4.17:
"the source code is licensed under Apache 2.0 which allows compiling binaries from source and then
distributing those versions").

Risks and how they are handled, most important first:

## 2. How the inventory was made

* `closure.json` written by `bp2cmake.py` lists the 115 modules of the closure; 81 are compiled and
  contribute objects to the library (2,350 sources). Modules that only export headers are excluded.
* Each compiled module's directory is resolved to its license metadata the way Soong does it: the nearest
  enclosing `Android.bp` with a `package { default_applicable_licenses }` and the `license` modules it
  names (`license_kinds`, `license_text`). `tools/gen_notices.py` does this at build time
  (section 7).
* Files that sit in a compiled project but are not compiled were checked separately (HarfBuzz and FreeType
  tests and m4 files, ICU test data, expat docs): they carry GPL, OFL, GFDL, CC-BY and similar licenses in
  AOSP's per-project license module, but none is linked. The generator lists the project's license kinds
  regardless, so the allow list in `config/notices-policy.toml` names them with a comment.
* The binary was inspected: `readelf -d` (NEEDED: libdl, libpthread, libm, librt, libc, ld-linux; no
  RUNPATH), `.comment` (clang 21.1.8, LLD 21.1.8, rustc 1.83.0, GCC 10.2.1 runtime objects), `strings` for
  build paths (none), `nm` for locally defined glibc symbols (`fstat`, `pthread_atfork`).

### 3.1 dng_sdk (Adobe)

Files read: `LICENSE`, `LICENSE.source_code`, `LICENSE.technology`, `NOTICE`, `PATENTS`, `METADATA`,
`Android.bp` in `external/dng_sdk`.

What the agreement gives: a non-exclusive, worldwide, royalty-free license "to use, reproduce, prepare
derivative works from, publicly display, publicly perform, distribute and sublicense the Software for any
purpose". "Software" is defined as the code "in any format", so object code is covered. The separate
`PATENTS` file is a royalty-free patent license for anything that reads or writes DNG-compliant files, with
a termination clause if the licensee sues Adobe over DNG.

What deserves attention:

1. **Section 5, indemnification.** "If you choose to distribute the Software in a commercial product, you
   do so with the understanding that you agree to defend, indemnify and hold harmless Adobe against any
   losses, damages and costs arising from the claims, lawsuits or other legal actions arising out of such
   distribution." Section 1 also says that any distribution "constitutes your acceptance of this Agreement".
   Our distribution is free and not a commercial product, but anyone who bundles our artifact into
   something they sell, and ships the library to customers, takes on this clause. A test-only dependency
   is not redistributed, so the normal Robolectric user is unaffected. The README says so.
2. **Section 2** requires keeping notices and including them "in any copies of the Software that you
   distribute in human-readable format". The binary is not human-readable, but we ship the notices file
   with it, which is the safe reading.
3. **Mandatory sentence**, from `LICENSE.technology` and `PATENTS`, "displayed in a prominent manner within
   its source code and documentation": *This product includes DNG technology under license by Adobe
   Systems Incorporated.* It is in the README and the notices file.
4. **Section 7**: rights terminate on a material breach. The risk is limited to failing to keep the notices.
5. **Section 6**: no use of the Adobe or DNG marks to endorse the product.
6. AOSP flags the project `license_type: BY_EXCEPTION_ONLY` and the METADATA header says to consult
   `opensource-licensing@google.com` before depending on it. Google's own redistribution of the official
   library carries the same terms, which is the best available evidence that the arrangement is accepted
   for this use.

Decision: dng_sdk stays in for parity (RAW/DNG decoding through `ImageDecoder` is part of the official
behaviour). The agreement is shipped and the README describes the exposure. Asking Adobe or Google for a
written statement is worth considering if the project grows. A build option that drops `SkRawCodec` and `libdng_sdk`
would remove the issue for people who care; it needs a small Skia patch, a parity check (the JNI tables
would not change) and a note that DNG decoding is then unavailable. Not implemented.

### 3.2 libjpeg-turbo and the IJG

libjpeg-turbo is covered by three licenses (IJG, BSD-3-Clause, zlib). For binary-only distribution its own
`LICENSE.md` says that product documentation must include: *This software is based in part on the work of
the Independent JPEG Group.* The TurboJPEG API clause (include the BSD text) applies if the binary uses
the TurboJPEG API; ship the BSD text regardless. `README.ijg` is in the tree but is not listed as
`license_text` in `Android.bp`, so the generator takes it from `config/notices-extra.toml`.

### 3.3 FreeType

FreeType says to choose exactly one of the FTL and GPLv2. We use the FTL: it is compatible with
everything else in the library, the GPL would not be. The FTL requires, for binary distribution, a
statement in the distribution documentation that the software is based in part on the work of the FreeType
Team; the suggested form is "Portions of this software are copyright (c) 2023 The FreeType Project
(www.freetype.org). All rights reserved." (2023 is the year of 2.13.2.) The "LGPL" entry in AOSP's
`external_freetype_license` kinds is a leftover of a bulk import: no file under `src/` or `include/`
mentions the GPL or LGPL (grep at the pin). The generator records this in the policy file as an
acknowledged exception with that reason.

### 3.4 libultrahdr and the Adobe Gain Map notice

`external/libultrahdr/Android.bp` attaches a second license module, `adobe_hdr_gain_map_license`, kind
`legacy_by_exception_only`, whose entire text is: *This product includes Gain Map technology under license
by Adobe.* The code is Apache-2.0. We have no terms beyond the sentence. Ship it verbatim.

### 3.5 libgcc and glibc pieces linked into the library

The link uses `-static-libgcc`, as Soong does on x86_64 hosts, so `libgcc.a` (compiler builtins and the
arm64 outline atomics) and the C runtime start/end objects are part of the library. They are GPL-3.0-or-later
with the GCC Runtime Library Exception 3.1, which permits propagating the combined work under other terms
provided the compilation process is "eligible". Compiling with clang from our own sources and linking
`libgcc.a` as a plain archive is the normal case for the exception. Ship the exception text (Debian's
`libgcc-10-dev` copyright file has it).

`nm` on the unstripped arm64 library shows two locally defined glibc symbols, `fstat` and `pthread_atfork`.
They come from `libc_nonshared.a` in glibc 2.31's `libc6-dev`, which the linker adds when linking against
`libc.so`. This is LGPL-2.1-or-later code. Obligations: the LGPL text, the glibc copyright notice, and the
ability for a recipient to replace the LGPL part. For a shared library whose complete source and build
scripts are public, relinking is possible, so section 6 of the LGPL is met in practice. The sysroot
keeps the Debian copyright files of libc6-dev and libgcc-10-dev and `usr/share/common-licenses`
(LGPL-2.1, GPL-3), and the notices include them. The link also takes `crti.o` and `crtn.o` from
glibc and `crtbeginS.o`/`crtendS.o` from GCC; they are covered by the same two entries.

### 3.6 WebP

libwebp is BSD-3-Clause with a separate "Additional IP Rights Grant (Patents)" (`PATENTS`): a royalty-free
patent license that ends for a licensee who starts patent litigation over WebM. Ship the file. No action
beyond that.

## 5. What we do not redistribute

* The official `libandroid_runtime.so` (x86_64, mac, windows) and the `android-all` jars. They stay on
  Maven Central; CI downloads them to compare against and discards them. Nothing in the public repository
  is derived from their code. Derived facts that are in the repository: the list of JNI method names and
  signatures (a fact about the Java API, which our own sources register as well), and the string
  evidence used by `rust/check-live.py` (not stored).
* The rig goldens (`tests/rig/goldens/x86_64/`, 37 images and 3 text files, 1.8 MB) are committed. They are
  pictures our own test scenes drew with the official library and contain no code from it. They do
  contain rendered glyphs and framework drawables: Noto fonts are OFL-1.1 or Apache-2.0 and the framework
  resources are Apache-2.0, so the rendered pixels are fine to publish. Committing them keeps the rig
  usable without the official library. The alternative, regenerating them in CI from the downloaded
  official library (about nine minutes under qemu per run), remains possible if a reviewer prefers it.
* AOSP sources are fetched at build time from `android.googlesource.com`, not copied into the repository.
* The Debian sysroot packages and the LLVM and Rust tarballs are fetched, verified and not committed.

## 6. License for our own files

**Apache-2.0** for the build scripts, CMake, tools, the loader plugin, the rig and the documentation
(`LICENSE`), with a short `NOTICE` that credits AOSP, Robolectric and the toolchain.

Reasons:

* It is the license of the code the scripts generate builds for (AOSP), and it is compatible with
  Robolectric's MIT license, so the loader change or the build recipe can be offered upstream as is.
* It has an explicit patent grant, which matters for a project that touches codecs.
* It is compatible with every component above (none is GPL).
* The loader plugin subclasses Robolectric's `DefaultNativeRuntimeLoader` and mirrors some of its logic
  (property names, extraction steps). Robolectric is MIT-licensed, so the plugin keeps an attribution
  in its source header and ships Robolectric's license text as `META-INF/LICENSE-robolectric.txt`.

The published binary is an aggregate: Apache-2.0 for our scripts, the licenses in section 3 for the library.
The Maven POM lists `Apache-2.0` as the project license and points at the bundled notices for the
binary. A single file named `THIRD_PARTY_NOTICES` inside the jar (`META-INF/`) and next to the `.so` in
release assets is the usual form.

The patches in `patches/frameworks/base/` are AOSP commits from later tags. They modify Apache-2.0 files,
which keep their headers, and each patch file starts with its provenance (commit, author, date, source
URL), which satisfies section 4(b) of the license.

## 7. Generating the notices at build time

Implemented in `tools/gen_notices.py`, `config/notices-policy.toml`, `config/notices-extra.toml` and
`cmake/notices.cmake` ([NOTES.md](NOTES.md), section "Notices", has the details).

* `tools/fetch.py` fetches the top-level license files (NOTICE, LICENSE, COPYING, MODULE_LICENSE_*,
  METADATA, PATENTS) of every project fetched in parts. `config/projects.toml` adds
  `build/soong/licenses` and the top-level `Android.bp` of hardware/interfaces and googletest,
  which hold license modules. Every module of the closure now resolves to a fetched license text.
* `toolchain/make-sysroot.py` keeps `usr/share/doc/*/copyright` and `usr/share/common-licenses`
  (the Debian copyright files of glibc and GCC refer to the latter for the full LGPL-2.1 and GPL-3
  texts); `toolchain/build-runtimes.sh` installs the LLVM `LICENSE.TXT` files next to the runtimes.
* Building `libandroid_runtime.so` writes `NOTICE` next to it, plus `notices.json`. The link runs
  with lld's `--why-extract`, so the file lists only what the linker took: module archives with at
  least one extracted member, the Rust crates of librustlibs.a, libc++, the UBSan runtime, the GCC
  crt objects, glibc's crti.o, crtn.o and libc_nonshared.a, and the header libraries of the
  closure. A linked archive or object without a license entry fails the build, as do the checks
  of the prototype (missing text, kind outside the policy, unacknowledged exception).

Result at the pin: 48 components, 55 distinct texts, 646 KB, no problems. 23 modules on the link
line contribute no object, so hardware/interfaces, expat, modp_b64 and libvintf are not in the
file (the table in section 3 lists them because they are on the link line).

For a release, `ci/build.sh` copies `build/out/lib/NOTICE` to the asset `THIRD_PARTY_NOTICES` and
`build/out/notices/libandroid_runtime/notices.json` next to it; inside the jar it goes to
`META-INF/THIRD_PARTY_NOTICES`. The four sentences of section 4 also go in the README.
